# CI, staging, and releases

| Environment | Git branch | App and data |
| --- | --- | --- |
| Development | Work branch | Next.js locally with a disposable Supabase CLI/Docker stack |
| Staging | `release/staging` | Vercel Preview with a separate Supabase project and synthetic Dictionary data |
| Production | `master` | Vercel Production with the production Supabase project |

GitHub administration is needed to manage repository merge settings and rulesets. Vercel project administration is needed for Git settings, environment variables, domains, and protection. The Supabase project owner or delegated operator provisions staging and applies reviewed database and Edge Function changes. QA needs Preview access, staging admin credentials, and a staging Supabase test user for browser-role checks.

## Phase 1 — Enable the GitHub gate

1. Land the GitHub Actions workflow on `master` through the existing PR process. Open a test PR against `master` and confirm that GitHub Actions emits the `PR gate` job check under the `4snow` workflow. Validate a passing PR and failing branch-name, PR-title, commit-subject, and quality checks. Confirm that updating the PR title and pushing commits rerun the check.
2. Once the check exists, verify GitHub plan support and activate an exact-branch ruleset for `master`. Require a PR and the observed `PR gate` check from GitHub Actions. Require the head to be up to date with the base and block force pushes and branch deletion. Keep bypass access empty where possible and record any exceptions. Set the independent review count according to available reviewers.
3. Allow squash and merge commits. Configure squash and merge-commit messages to use the PR title. Release and synchronization PRs need merge commits, so keep linear history enforcement off. Verify rule enforcement on a test PR and record the ruleset, check source, and bypasses before starting Phase 2. [GitHub rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)

The same workflow checks PRs targeting `release/staging`. Use a Conventional Branch name for work branches, such as `feat/dictionary-search` or `codex/staging-preview-config`. Use scoped Conventional Commits for PR titles and authored commit subjects, such as `fix(dictionary): preserve release attribution`. The long-lived `master` branch can be the source of a PR that synchronizes `release/staging`. See [Conventional Branch](https://conventionalbranch.org/) and [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/).

## Phase 2 — Prepare the Supabase staging backend

1. Create a separate Supabase project for staging. In the dashboard, record its organization, project reference, and API URL alongside the production reference. Cross-check the reference in the project URL and API URL, confirm the references differ, and use an explicit staging target before each remote write. Keep production data out of staging. For an existing staging project, verify the baseline, take a backup, and establish the restore procedure before changes. [Supabase environments](https://supabase.com/docs/guides/deployment/managing-environments)
2. Check out the reviewed app SHA. Inspect the remote migration history, the current schema, and all pending files. At this revision the Dictionary inventory is the timestamp-ordered set of tracked migrations matching `supabase/migrations/*_vtv_*.sql`. Review any future additions and dependencies by feature. `20261115000001_quiz_baseline.sql` falls inside that timestamp range and remains local-only, along with `quiz-submit`. If a Dictionary change depends on Quiz, stop for a reviewed prerequisite change. [Quiz rollout prerequisites](features/quiz-trusted-submissions.md)
3. Use an isolated Supabase CLI working directory for the approved migration set. Copy the reviewed Dictionary files byte-for-byte into its `supabase/migrations/`, with the repository's `supabase/config.toml` under `supabase/`. Omit seed files. Keep the directory outside the tracked checkout. With a pinned CLI, verify the supported flags with `--help`. For CLI v2, the preflight from that directory is:

   ```powershell
   supabase link --project-ref <staging-ref>
   supabase migration list --linked
   supabase db push --linked --dry-run
   ```

   Confirm the linked reference against the dashboard and compare the dry-run list to the approved pending inventory. If history or schema differs, a dependency is missing, or the dry run asks to insert an older file, reconcile it with the database owner before proceeding. Apply with `supabase db push --linked` from that same isolated directory only after approval, then run `supabase migration list --linked` again. Preserve original migration timestamps and reconcile future deployments against this history. Keep the full checkout's migration push and automatic seed out of the staging procedure. [Supabase CLI workflow](https://supabase.com/docs/guides/local-development/cli-workflows)
4. Check RLS and grants against the migration review. The Data API must expose `public.vtv_current_release` and `public.vtv_releases` for player reads, while `private` stays outside the exposed schemas and trusted Dictionary RPCs stay denied to browser roles. Review staging Auth settings for the test user. If an Auth flow uses redirects, allow its exact staging URL. Check Realtime and Storage configuration for the specific features included in QA.
5. From the complete checkout at the same SHA, deploy only `vtv-dictionary` with `supabase functions deploy vtv-dictionary --project-ref <staging-ref>` on CLI v2. Its `verify_jwt = false` gateway setting lets it receive the app's custom admin JWT. The function itself verifies the token. Supabase injects `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`. The latter stays inside the trusted function environment. [Edge Function deployment](https://supabase.com/docs/guides/functions/deploy)

## Connect Vercel Preview

1. Verify the Vercel project's connected Git repository and confirm **Production Branch** is `master`. Versioned [Git deployment settings](../vercel.json) allow `master` and `release/staging`. Vercel accepts overlapping rules when one matching rule is enabled. These settings need to be present in the revision Vercel evaluates. Check existing branches and Preview defaults before provisioning so an older branch revision cannot fall back to production values. [Vercel Git configuration](https://vercel.com/docs/project-configuration/git-configuration)
2. Bootstrap `release/staging` at the reviewed `master` commit containing the CI workflow and deployment settings. Assign a stable HTTPS branch URL or a dedicated domain tracked to `release/staging`. Enable [Deployment Protection](https://vercel.com/docs/deployment-protection) for Preview as supported by the plan and check access from an unauthorized browser. Before staging is ready, any bootstrap Preview must use safe Preview defaults with Dictionary disabled and without production credentials or data access.
3. In the Vercel project's environment variables, select **Preview**, then the Git branch **`release/staging`**, for each entry below. Use staging values from the verified project and store private values directly in provider secret settings or an approved password manager. [Branch-specific Preview variables](https://vercel.com/docs/environment-variables/manage-across-environments)

   | Vercel variable | Staging value |
   | --- | --- |
   | `NEXT_PUBLIC_SUPABASE_URL` | Staging API URL such as `https://<staging-ref>.supabase.co` |
   | `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Matching browser-safe staging anon key |
   | `NEXT_PUBLIC_VTV_IMPORT_ENABLED` | `true` to expose the Dictionary admin workflow |
   | `ADMIN_USERNAME`, `ADMIN_PASSWORD` | Dedicated private staging credentials |
   | `ADMIN_JWT_SECRET` | Private staging signing secret, distinct from production |
   | `ADMIN_TOKEN_EXPIRES_IN` | Optional server-only lifetime. Omit to use the app default |

4. Set matching `ADMIN_JWT_SECRET` in the staging Supabase Edge Function secrets. Set `VTV_ALLOWED_ORIGINS` to the exact stable HTTPS Preview origin, with no path, trailing slash, or wildcard. If multiple origins have been approved, enter them comma-separated. Store only variable names and public origins in the handoff. [Edge Function secrets](https://supabase.com/docs/guides/functions/secrets)
5. Build a fresh Git Preview from `release/staging` so Vercel picks up the scoped variables. Verify the stable branch alias, immutable deployment URL, commit SHA, and Preview environment in the dashboard. Check that a disposable work-branch revision containing `vercel.json` does not trigger a Git deployment. Confirm that `master` still tracks Production without making a separate production deployment for the check. [Vercel Preview URLs](https://vercel.com/docs/deployments/environments)

## Verify Dictionary on staging

Use the stable Preview origin for the live browser journey. Record the immutable deployment URL and full Git SHA in the QA result so the evidence survives subsequent updates to the branch alias.

1. Open `/admin` and verify successful staging login, rejected invalid credentials, and an authenticated Dictionary operation. In browser network requests, confirm the API hostname has the staging project ref. Inspect the preflight and response to `/functions/v1/vtv-dictionary`. The allowed response must return the exact staging origin. Using requests with staging browser credentials, check `401` for missing and invalid admin tokens and rejection of a disallowed origin (`403` with no allow-origin header).
2. Prepare a staging-only copy of [the synthetic import fixture](../tests/vua-tieng-viet/fixtures/synthetic.json). Assign distinct artifact and source IDs and revisions for this rehearsal. Use reviewed synthetic provenance and recorded rights evidence, and label the source and review notes for staging QA. For an empty Dictionary, include one distinct candidate with a Vietnamese definition per supported normalized length (3, 5, 7, and 9), for example *mèo*, *hoa lá*, *đất nước*, and *tiếng Việt*. Keep source entry and external IDs unique and update the source reference on each entry. Retain the reviewed fixture and its source fingerprint for a repeatable run.
3. As staging admin, preview and finalize the import at `/admin#dictionary/import`. Confirm the candidates are pending. With the anon key and then with a real staging Supabase Auth session, verify that a direct Data API read of `private.vtv_entries` using `Accept-Profile: private` is denied. Verify that calling `/rest/v1/rpc/vtv_candidate_detail` with the fixture candidate's ID as `p_entry_id` is denied to both roles. If the API reports that the routine is unavailable, verify the routine exists and its grants exclude the browser roles before recording the result. The app admin JWT is only for the trusted Edge Function.
4. At `/admin#dictionary/review`, record the staging-only source rights decision after reviewing the evidence, then approve the candidates and mark the intended answers eligible. At `/admin#dictionary/publish`, preview a complete Dictionary release, confirm every level has an eligible answer and sample play shows the intended definition and attribution, then publish. Verify the current release pointer matches the publish result and a new round on `/vua-tieng-viet` uses the staged data. Check that both browser roles can read the published release, their writes are denied, and private source and editorial fields are absent from the player payload. [Dictionary publication requirements](features/vua-tieng-viet-dictionary.md#7-publication-and-concurrency)
5. Record the SHA, stable origin, immutable URL, staging ref, reviewed/applied migration versions, deployed function revision, fixture revision, release ID, and the pass/fail result for each check. Keep tokens, passwords, secret values, and unredacted request captures out of the evidence. Use the disposable local stack for suites that reset tables, clear rate limits, or install test triggers. Preserve staging audit and release history.
6. After smoke passes, protect `release/staging` with its own GitHub ruleset. Require PRs and the observed `PR gate` from GitHub Actions. Block direct updates, force pushes, and deletion. Keep the up-to-date requirement off for this branch so a production hotfix can be synchronized while staging has unreleased work. Verify the rules with a test PR and confirm an approved merge still creates the staging deployment.

## Release and synchronization

1. Squash work PRs into `release/staging`. QA the resulting Preview SHA. Open a scoped Conventional Commit PR such as `chore(release): promote staging to production` from `release/staging` into `master`. Attach QA evidence and verify the head is still the QA SHA and includes the current `master`. If the base or staging content changes, synchronize through a PR first and QA the new Preview before releasing.
2. For backend changes, review the production schema baseline and migration history separately. Record operator approval, the reviewed SQL/function revision, deployment order, and recovery point. Apply only the approved backend scope, preserving compatibility with the currently served app and the pending app. If the changes require a coordinated cutover, prepare and approve its order before merging. Supabase production changes are separate operator steps.
3. Merge the release PR with a merge commit. Vercel builds the `master` merge SHA using Production variables. Verify that deployment, its domain and project ref, and production smoke results. Use Git Integration for the production build so credentials and configuration come from the Production environment.
4. Synchronize `master` back to `release/staging` via PR with a merge commit so both branches retain the release history. Repeat QA for the next release candidate. For a hotfix, branch `hotfix/<description>` from `master`, merge through the protected PR and CI flow, then synchronize `master` back into `release/staging` before the next QA. If a synchronization PR has conflicts, resolve them on a work branch from `release/staging` by merging `master` into it, then open a synchronization PR from that branch and use a merge commit.

## Rollback and recovery

- **Staging failure** — Block the release PR. Record the failing Preview SHA and the affected backend versions, repair through a work PR, and QA the new Preview SHA.
- **Production app failure** — If the last known good Production deployment is compatible with the current backend, use Vercel Instant Rollback to restore it. Verify the production domain and smoke result. Follow with a revert or fix PR into `master` and synchronize staging, so the next Git deployment preserves the fix. [Vercel Instant Rollback](https://vercel.com/docs/instant-rollback)
- **Database or Edge Function failure** — Check app/backend compatibility before restoring an earlier function version. Use a reviewed forward-fix migration for schema recovery or a tested backup restore for data loss. Verify history, data, grants, RLS, and the public release pointer after recovery. For a bad Dictionary release, publish a corrected release and retain the previous release's audit history. [Supabase recovery guide](supabase.md#routine-operations-and-recovery)
